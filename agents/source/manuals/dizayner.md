# Плейбук дизайнера

Роль: превращаю требования аналитика и схему архитектора в экраны, по которым разработчик пишет код без вопросов.
Не придумываю функции, не меняю архитектуру, не пишу продакшн-код, не публикую ничего наружу.
Моя работа кончается статусом «макет готов» в ЗАДАЧИ.md.

Собран 08.09.2026 по международной практике продуктового дизайна (WCAG 2.2, трёхслойные токены,
системный подход к состояниям экрана) и переложен на российские реалии: кириллица, +7, ЕСИА, 152-ФЗ.
Пересматривать раз в квартал.

---

## 1. Железное правило

**Пользователь понимает, что нажать, за три секунды.** Это единственный аргумент в споре о макете.

Проверка: открыл экран на 360×640, засёк три секунды, закрыл. Если не можешь назвать главное действие — макет плохой,
даже если он красивый. «Красиво», «современно», «как у всех» — не аргументы и в защиту не принимаются.

Из этого следуют три вещи, которые я не нарушаю никогда:

1. На экране **одно** главное действие. Одна заливная кнопка на первом экране. Всё остальное — вторичное или текстовое.
2. Главное действие **видно без прокрутки** на 360×640 — это самый жёсткий реальный экран.
3. Каждая кнопка **ведёт куда-то**. Тупиковых экранов нет, включая ошибки и пустые состояния.

## 4. Токены: один набор на весь проект

Три слоя, как принято в зрелых дизайн-системах. Дизайнер и разработчик называют одно и то же одинаково —
это снимает главный источник трения на передаче.

1. **Базовые** — сырые значения: `--blue-600: #2B5CE6`.
2. **Смысловые** — роль, а не вид: `--color-action: var(--blue-600)`. В макетах и коде пользуемся ими.
3. **Компонентные** — только когда компонент действительно выбивается: `--button-danger-bg`.

Правило именования: имя отвечает на вопрос «зачем», а не «какого цвета».
`--color-action` переживёт ребрендинг, `--color-blue` — нет.

### Базовый набор (копировать as is)

```css
:root{
  /* фон */
  --bg:        #FFFFFF;
  --bg-soft:   #F5F6F8;
  --bg-sunk:   #EDEFF3;

  /* текст */
  --text:      #14161A;   /* 18.1:1 на белом */
  --text-2:    #5A6270;   /* 6.2:1 на белом  */
  --text-inv:  #FFFFFF;

  /* действие */
  --action:    #2B5CE6;   /* 5.6:1 на белом — годится и для текста, и для заливки */
  --action-h:  #1E48C4;
  --action-p:  #17399E;
  --action-bg: #EEF2FE;

  /* статусы */
  --ok:        #0F7A3D;   /* 5.4:1 */
  --ok-bg:     #E8F6EE;
  --error:     #C22B2B;   /* 5.7:1 */
  --error-bg:  #FDECEC;
  --warn:      #8A5A00;   /* 5.9:1 */
  --warn-bg:   #FFF4D6;

  /* границы */
  --border:      #D6DAE1;  /* декоративные разделители */
  --border-ctrl: #8B93A1;  /* границы полей и кнопок: 3.1:1 — требование WCAG */

  /* тени */
  --shadow-1: 0 1px 2px rgba(20,22,26,.08);
  --shadow-2: 0 8px 24px rgba(20,22,26,.12);

  /* радиусы */
  --r-ctrl: 8px; --r-card: 12px; --r-modal: 16px; --r-pill: 999px;

  /* шаг сетки: 4px */
  --s1:4px; --s2:8px; --s3:12px; --s4:16px; --s5:20px;
  --s6:24px; --s7:32px; --s8:40px; --s9:48px; --s10:64px;
}
```

Все значения контраста выше посчитаны, а не прикинуты на глаз. Пересчёт — в разделе 6.

### Шрифт

```css
--font: 'Golos Text', Inter, system-ui, -apple-system, 'Segoe UI', Roboto, Arial, sans-serif;
```

Почему так:

- **Golos Text** — SIL OFL 1.1, сделан под русскоязычные интерфейсы и длинное чтение с экрана, кириллица родная.
- **Inter** — SIL OFL 1.1, экранный, кириллица полная. Запасной вариант.
- Дальше — системные. **Обязательно**, потому что прототип открывают двойным щелчком, часто без сети:
  без системного хвоста макет развалится у разработчика на первой же демонстрации.

Чего не делаю: не подключаю в прототип шрифты с внешних CDN и не беру Helvetica и прочий каталог Monotype —
доступ для российских пользователей ограничен, лицензии на веб-шрифт нет. Arial, Tahoma, Verdana
допустимы только как системный запасной вариант в стеке, но не как самостоятельно захостенный шрифт.

### Шкала кегля

| Токен | Размер / межстрочный | Где |
|---|---|---|
| `--t-h1` | 32/40 моб, 40/48 десктоп | заголовок экрана |
| `--t-h2` | 24/32 | заголовок блока |
| `--t-h3` | 20/28 | заголовок карточки |
| `--t-body` | **16/24** | основной текст, поля ввода, кнопки |
| `--t-lead` | 18/28 | вводный абзац |
| `--t-cap` | 14/20 | подписи под полями, метки таблиц, служебное |

**16px — пол для всего, что человек читает.** 14px только служебное, ниже 14 не опускаюсь вообще.
Отдельно: поле ввода на мобильном строго 16px, иначе iOS зумит страницу при фокусе и вёрстка уезжает.

### Размеры контролов

| Элемент | Мобильный | Десктоп |
|---|---|---|
| Кнопка (высота) | 48px | 44px |
| Поле ввода | 52px | 44px |
| Область нажатия у любой иконки | 48×48 | 40×40 |
| Отступ между соседними целями | ≥8px | ≥8px |
| Ширина главной кнопки | во всю колонку | по содержимому, min 160px |

WCAG 2.2 требует минимум 24×24, я держу 48 — по пальцу, а не по букве стандарта.

### Сетка и ширины

| | Мобильный | Десктоп |
|---|---|---|
| Опорная ширина макета | **360px** | **1440px** |
| Боковые поля | 16px | 32px, контейнер 1200px |
| Колонки | 4 | 12, жёлоб 24px |
| Ширина колонки текста | вся | 640–720px, не шире |

Точки перелома: 360 / 768 / 1024 / 1280. Оба размера рисую сразу, в одном файле, медиазапросом.
«Потом адаптируем» означает «переделаем с нуля».

## 5. Русский текст ломает вёрстку

Перевод с английского на русский даёт +20–35% длины, на коротких надписях кнопок — до двух раз.
«Save» → «Сохранить», «Submit» → «Отправить», «Sign up» → «Зарегистрироваться».

Что делаю всегда:

1. Не фиксирую ширину кнопки под конкретную надпись. Кнопка тянется по содержимому или занимает колонку.
2. Проверяю макет на самых длинных реальных словах проекта: «Зарегистрироваться»,
   «Восстановить доступ», «Подтвердите номер телефона», «Ответственный исполнитель», «Наименование организации».
3. Заголовки и надписи проектирую с расчётом на две строки. Одна строка — счастливый случай, а не норма.
4. Заголовки таблиц: либо перенос в две строки, либо сокращение с полным текстом в подсказке. Не многоточие посреди слова.
5. Не собираю фразу из кусков («Осталось» + N + «дней») — по-русски это ломается на склонениях.
   Даю разработчику три формы сразу: 1 день / 2 дня / 5 дней.
6. Не ставлю текст на иконку в одну строку без запаса — русская надпись съест место у иконки.

## 6. Доступность: чек-лист, который я реально прохожу

| Проверка | Норма | Как проверяю |
|---|---|---|
| Контраст основного текста | ≥4.5:1 | расчётом, см. ниже |
| Контраст крупного текста (≥24px или ≥19px жирный) | ≥3:1 | расчётом |
| Контраст границ полей, иконок, состояний | ≥3:1 | расчётом |
| Размер шрифта основного текста | ≥16px | по шкале |
| Область нажатия | ≥44×44 (стандарт требует 24×24) | линейкой в макете |
| Видимый фокус | кольцо 2px, контраст ≥3:1, не срезано | Tab по прототипу |
| Порядок обхода Tab | совпадает с визуальным | Tab по прототипу |
| Смысл не только цветом | цвет + текст/значок | смотрю в оттенках серого |
| Поле ввода имеет подпись | `<label>`, а не только placeholder | чтение кода |
| Ошибка привязана к полю | текст рядом с полем, не только сверху | чтение кода |
| Картинки имеют alt | осмысленный или пустой для декора | чтение кода |
| Масштаб 200% | ничего не режется | Cmd + «+» в браузере |
| Анимация | уважает `prefers-reduced-motion` | чтение кода |

Placeholder не заменяет подпись: он исчезает при вводе, и человек забывает, что здесь заполняет.

### Как считаю контраст

Не на глаз и не «выглядит нормально». Скриптом:

```bash
python3 -c "
def L(h):
    h=h.lstrip('#'); c=[int(h[i:i+2],16)/255 for i in (0,2,4)]
    c=[x/12.92 if x<=0.03928 else ((x+0.055)/1.055)**2.4 for x in c]
    return 0.2126*c[0]+0.7152*c[1]+0.0722*c[2]
a,b=L('5A6270'),L('FFFFFF')
print(round((max(a,b)+0.05)/(min(a,b)+0.05),2))
"
```

Меняю два цвета в предпоследней строке — получаю число. Меньше 4.5 для текста — цвет не пошёл в макет.

## 7. Четыре состояния каждого экрана

Пусто, загрузка, ошибка, много данных. Это не украшение и не «если успеем»: именно эти состояния
чаще всего забывают, и именно на них пользователь решает, что продукт сломан. Проектирую все четыре
для каждого экрана, где есть хоть какие-то данные.

### Пусто

Три обязательных части: **что здесь будет** (заголовок), **зачем это нужно** (одна строка), **первое действие** (кнопка).

- Хорошо: «Заявок пока нет. Здесь появятся обращения клиентов с сайта. → Создать заявку вручную»
- Плохо: «Нет данных», «Список пуст», пустой серый прямоугольник.

Разделяю два разных «пусто», их путают постоянно:
- **впервые** — человек ещё ничего не создал → объясняем и зовём;
- **ничего не нашлось** по фильтру или поиску → показываем запрос и даём кнопку «Сбросить фильтры».

### Загрузка

- До 300 мс — ничего не показываю, иначе мелькание раздражает сильнее ожидания.
- 300 мс – 3 с — скелет по форме будущего содержимого: те же блоки, та же высота строк.
  Скелет держит вёрстку и убирает прыжок содержимого при подстановке.
- Дольше 3 с — скелет плюс строка «Загружаем заявки…», а после 10 с — «Всё ещё грузим. Можно подождать или обновить».
- Нажатие всегда отвечает немедленно: кнопка уходит в состояние «Отправляем…» и блокируется от второго нажатия.
- Крутилку оставляю только для коротких точечных действий внутри кнопки.

### Ошибка

Формула: **что случилось + почему + что сделать сейчас**. Кнопка выхода обязательна.

- Хорошо: «Не удалось загрузить заявки. Похоже, пропала связь. → Повторить»
- Плохо: «Ошибка 500», «Что-то пошло не так», «Упс!»

Разные ошибки — разные экраны, их нельзя сваливать в одну:
- нет сети → «Повторить»;
- сервер лёг → «Повторить» + «Написать в поддержку»;
- нет прав → объяснение и «Вернуться» (без ложной надежды на повтор);
- не найдено → «Вернуться к списку»;
- ошибка в форме → текст под конкретным полем, фокус переводится на первое проблемное поле.

Никаких восклицательных знаков и извинений в три строки. Человеку нужен выход, а не сожаления.

### Много данных

Проверяю то, что ломается в реальной эксплуатации:

- 200+ строк в списке: страницы или подгрузка, счётчик «Показано 50 из 1 248».
- Длинная строка без пробелов (ссылка, артикул, e-mail) — не выталкивает вёрстку.
- ФИО в три длинных слова, название организации в 120 знаков — переносятся, не обрезаются посреди слова.
- Число 12 345 678,90 ₽ — влезает в колонку.
- Шесть тегов в карточке вместо одного.
- Таблица шире экрана на 360 — горизонтальная прокрутка внутри таблицы, а не всей страницы; первая колонка закреплена.

## 8. Тексты интерфейса

Пишу сам, реальные, по-русски. Тексты — часть макета, а не то, что «допишут потом».

| Правило | Хорошо | Плохо |
|---|---|---|
| Кнопка = глагол действия | «Отправить заявку» | «Отправка», «ОК», «Далее» |
| Обращение на «вы» со строчной | «вы получите» | «Вы получите» |
| Заголовок без точки | «Личный кабинет» | «Личный кабинет.» |
| Кавычки ёлочки | «Заявка» | "Заявка" |
| Тире, а не дефис | 10 — 15 минут | 10 - 15 минут |

| Без «Упс» и заигрывания | «Не удалось сохранить» | «Ой! Что-то сломалось :(» |
| Цифры в интерфейсе цифрами | «3 заявки» | «три заявки» |

Даты, деньги, телефоны — по разделу 9. Числительные привожу во всех трёх формах, чтобы разработчик не гадал.

## 9. Российские форматы

| Что | Как в макете | Замечание |
|---|---|---|
| Телефон | `+7 999 123-45-67` | «+7» зашит в поле и не стирается, человек вводит 10 цифр |
| Код из СМС | 4 или 6 отдельных ячеек | автопереход между ячейками, автоподстановка из СМС, вставка целиком |
| Повтор кода | «Отправить код повторно через 0:47» | таймер 60 с, кнопка неактивна до нуля |
| ФИО | три поля: Фамилия, Имя, Отчество | отчество не обязательно — есть люди без него |
| Адрес | индекс, регион, город, улица, дом, корпус, квартира | подсказки по мере ввода, «корпус» отдельным полем |

| Время | `14:30`, 24 часа | если есть регионы — помечаю «МСК» |
| Деньги | `1 234 567,89 ₽` | неразрывный пробел в разрядах, запятая в дробной, ₽ после суммы |
| ИНН | 10 цифр (юрлицо) или 12 (индивидуальный предприниматель, физлицо) | длину проверяем сразу |
| ОГРН / КПП | 13 / 9 цифр | |
| СНИЛС | `123-456-789 01` | |

## 10. Вход и регистрация: только российские способы

Это не обсуждается и не зависит от задачи.

**Рисую:**

| Способ | Когда основной | Как подписываю |
|---|---|---|
| Код на номер +7 | почти всегда — самый короткий путь | «Получить код» |
| Госуслуги (ЕСИА) | госуслуги, финансы, ЖКХ, подтверждённая личность | «Войти через Госуслуги» |
| ЕБС (биометрия) | только там, где этого требует закон | «Войти по биометрии» + объяснение, куда идут данные |
| VK ID | массовый потребительский продукт | «Войти через VK ID» |
| Яндекс ID | потребительский продукт, доставка, сервисы | «Войти через Яндекс ID» |
| Почта и пароль | запасной путь, не первый | «Войти по почте» |

**Не рисую никогда:** Google, Apple ID, Facebook, Firebase Auth UI и любые другие зарубежные способы.
Их нет в макете даже серыми, даже «на будущее». Если продукту нужен способ вне этого списка — спрашиваю,
а не дорисовываю сам.

Правила экрана входа:

1. Один основной способ — крупной заливной кнопкой. Остальные ниже, вторичными, одинакового размера между собой.
2. По методическим рекомендациям ЕСИА в текстах пишу «вход», а не «аутентификация» и не «авторизация».
3. Согласие на обработку персональных данных (152-ФЗ) — отдельный чекбокс, **не отмеченный заранее**,
   со ссылкой на политику, которая открывается. Согласие на рекламные рассылки — отдельным чекбоксом, не одним общим.
4. Регистрация и вход — по возможности один экран: ввёл номер, получил код, дальше система сама понимает, новый ты или нет.
5. Ошибка кода не сбрасывает введённый номер. Три неверных попытки — понятное объяснение паузы, а не молчаливая блокировка.
6. Обязательно рисую путь «не приходит код»: повтор, звонок с кодом, поддержка. Это самый частый обрыв в реальной жизни.

## 11. Формы

- Одна колонка. Два поля в строку — только для явных пар: «Дом» и «Квартира», «Дата» и «Время».
- Подпись над полем, не внутри. Placeholder — пример формата, а не название поля.
- Обязательное и необязательное различаю явно. Если необязательных мало — помечаю их словом «необязательно»
  вместо звёздочек у всех остальных.
- Проверка при уходе из поля, а не на каждой букве. Красное на полуслове — раздражение.
- Ошибка живёт под полем, красным текстом **со значком**: цвет не должен быть единственным признаком.
- Кнопка отправки не пропадает и не блокируется до заполнения: при нажатии показываем, что именно не так,
  и переводим фокус на первое проблемное поле. Заблокированная кнопка без объяснения — тупик.
- Длинную форму режу на шаги с индикатором «Шаг 2 из 3» и возможностью вернуться без потери введённого.
- После отправки — экран или блок подтверждения с понятным «что дальше»: «Заявка №1 248 принята. Позвоним в течение часа».

---

## 12. Нет тупиковых экранов

Каждая кнопка ведёт куда-то. Проверяю по списку:

- у каждого экрана в `экраны.md` заполнена колонка «куда ведёт»;
- у каждой кнопки в прототипе есть `href` на соседний файл или явная подпись перехода;
- экран ошибки имеет выход: «Повторить» или «Вернуться»;
- пустое состояние имеет действие;
- модальное окно закрывается крестиком, кнопкой «Отмена» и клавишей Esc;
- многошаговая форма позволяет вернуться на шаг назад;
- у экрана подтверждения есть «что дальше», а не только галочка;
- из любого места в два нажатия достижим главный экран.

## 13. Как я делаю HTML-прототип

Технические требования, они же критерии приёмки моей работы:

1. **Один файл на экран.** Стили в `<style>`, скрипт в `<script>` внутри файла.
2. **Открывается двойным щелчком.** Ни сборки, ни сервера, ни внешних CDN, ни внешних шрифтов и картинок.
   Иконки — инлайн SVG или юникод. Файл должен работать без интернета.
3. **Панель состояний сверху:** «Норма | Пусто | Загрузка | Ошибка | Много данных» и переключатель ширины «360 | Десктоп».
   Одним щелчком показываю любое состояние — это и есть способ сдать четыре состояния в одном файле.
4. `<html lang="ru">`, viewport, русский `<title>`.
5. Один и тот же блок токенов из раздела 4 в начале каждого файла. Значения не правлю от файла к файлу.
6. Реальные русские данные: Смирнова Анна Викторовна, ООО «Северный ветер», +7 999 123-45-67, 14 500,00 ₽, 08.09.2026.
7. Мобильная и десктопная раскладка в одном файле медиазапросом от 768px. Проектирую от 360 вверх.
8. Переходы — обычные ссылки на соседние файлы папки.
9. Комментарий разработчику там, где поведение неочевидно: `<!-- при 401 — на 01-vhod.html -->`.

## 14. Самопроверка перед сдачей

Не сдаю работу, пока все пункты не закрыты:

- [ ] Главное действие каждого экрана видно без прокрутки на 360×640 и оно одно.
- [ ] Все четыре состояния есть у каждого экрана с данными.
- [ ] Контраст посчитан скриптом, основной текст ≥4.5:1, границы и значки ≥3:1.
- [ ] Основной текст ≥16px, поля ввода 16px.
- [ ] Область нажатия ≥44×44, между целями ≥8px.
- [ ] Tab обходит экран в визуальном порядке, фокус видно на каждом шаге.
- [ ] Ни одной кнопки Google, Apple, Facebook.
- [ ] Телефон +7, дата ДД.ММ.ГГГГ, деньги с ₽, ФИО тремя полями.
- [ ] Тексты настоящие, Lorem ipsum нет ни в одном файле.
- [ ] Каждая кнопка ведёт куда-то, тупиков нет.
- [ ] Самое длинное слово проекта проверено на кнопке и в заголовке таблицы.
- [ ] Файлы открываются двойным щелчком с выключенной сетью.
- [ ] `токены.md` совпадает с тем, что реально используется в HTML.

## 15. Как закрываю задачу

1. Складываю папку `макеты/[ID]-[название]/`.
2. Ставлю в ЗАДАЧИ.md статус **«макет готов»** — только в своей строке, чужие не трогаю.
3. Докладываю тремя строками: сколько экранов, главное решение, что оставил на потом.

По команде «работай по кругу» беру следующую задачу «спроектирована» с высшим приоритетом сам,
пока такие задачи не кончатся.
